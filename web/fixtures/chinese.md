## 遷移前的準備

舊主機上的 `binpkg` 目錄已經累積了三年的套件，總大小約 1.8 TB。遷移前要先確認新主機的磁碟配置、網路頻寬與簽章金鑰都已就緒，否則同步到一半中斷時，鏡像站會拿到不完整的索引檔，使用者執行 `emerge --getbinpkg` 時就會看到校驗失敗。為了避免這種情況，我們先在新主機上建立唯讀的預備目錄，等全部檔案同步完成、`Packages` 索引重新產生並簽章後，才把對外的網址切換過去。

切換時間選在週日凌晨三點，這是一週中下載量最低的時段。根據過去一個月的存取紀錄，這個時段每小時的請求數不到尖峰時段的十分之一；即使切換過程中出現短暫錯誤，受影響的使用者也很少。切換完成後保留舊主機七天，確認沒有問題再關機。

### 檢查項目

1. 新主機的 `make.conf` 與舊主機一致，特別是 `CHOST`、`CFLAGS` 與 `FEATURES`。
2. 簽章金鑰已匯入，`gpg --list-secret-keys` 能列出 `A1B2C3D4` 結尾的金鑰。
3. 防火牆開放 `80`、`443` 與 `873` 連接埠。

> 注意：「預備目錄」與「正式目錄」必須在同一個檔案系統上，否則最後一步的 `mv` 不是原子操作。

### 主機規格比較

| 項目 | 舊主機 | 新主機 | 備註 |
| --- | --- | --- | --- |
| 處理器 | 8 核心 | 32 核心 | 編譯 `www-client/chromium` 的時間從九小時縮短到兩小時 |
| 記憶體 | 32 GB | 128 GB | `tmpfs` 編譯目錄改為 24 GB |
| 儲存空間 | 2 TB SSD | 8 TB HDD 加 2 TB NVMe | 套件放在 HDD，編譯暫存放在 NVMe |
| 網路 | 1 Gbps | 10 Gbps | 對外頻寬仍受機房上限限制 |

#### 同步指令

```bash
# 第一次完整同步：保留權限與時間戳記，並顯示進度
rsync -aH --info=progress2 old-host:/var/cache/binpkgs/ /srv/binpkgs-staging/

# 重新產生索引並簽章（需要先解鎖金鑰）
PKGDIR=/srv/binpkgs-staging emaint binhost --fix
gpg --detach-sign --armor /srv/binpkgs-staging/Packages
```

## 迁移后的验证

切换完成后，需要从三个不同地区的客户端分别执行一次完整的更新，确认索引、签名和下载速度都正常。北京和上海的客户端通过国内镜像访问，台北的客户端直接访问主站；三地都要记录 `emerge` 的输出和耗时，与迁移前的基线对比。如果任何一地的下载速度比基线低三成以上，就要检查 CDN 的缓存命中率，必要时回滚到旧主机。

验证期间，镜像站的同步频率从每六小时一次调高到每小时一次，这样发现问题后修复的结果能更快到达用户。验证结束后再恢复原来的频率，避免给上游带来不必要的负载。

### 常见问题

- **签名校验失败**：通常是镜像站拿到了旧的 `Packages.asc` 和新的 `Packages`，等下一次同步即可恢复。
- **下载速度慢**：先用 `curl -o /dev/null -w '%{speed_download}'` 测量单个文件的速度，再判断是网络问题还是服务器负载问题。
- **找不到套件**：确认客户端的 `PORTAGE_BINHOST` 已经指向新的网址，并且 `binrepos.conf` 里没有残留的旧条目。

### 回滚步骤

```python
# 回滚脚本：把对外网址切回旧主机，并通知镜像站重新同步
import subprocess

MIRRORS = ["mirror-bj", "mirror-sh", "mirror-tw"]

def rollback() -> None:
    # 先切换 DNS，再逐个通知镜像站；任何一步失败都立即停止
    subprocess.run(["dns-switch", "binhost", "old-host"], check=True)
    for name in MIRRORS:
        subprocess.run(["ssh", name, "systemctl", "start", "binpkg-sync"], check=True)
        print(f"已通知 {name} 重新同步")
```
